# 段階2b: 業績予想の修正のお知らせ全部を、数字の表と一緒に LLM に読ませ、始値の後の向きを点数で答えさせる — 事前宣言

宣言日: 2026-11-03。進め方は同じ日にユーザーの OK をもらった案のとおり。

## なぜやるか

段階2a では「+10% 以上の上方修正」だけを対象に、「理由は何か・続くか」を聞いて組に分けた。
1日では分かれず、20日では分かれたように見えたが、会社が分かったものに偏っていた (探索、合否には使っていない)。
2a の聞き方には次の不足があった。

- お知らせの文字しか渡しておらず、判断に要る数字 (どれくらい意外か、開示の前にどれだけ上がっていたか、決算期の何か月目か) が無かった
- 「始値の時点で修正の向きはほぼ値段に入っている」という前提を伝えていなかった
- 上方修正の一部だけで、下方修正や小さい修正を見ていなかった

ここでは対象を広げ、材料をそろえて、LLM に向きを直接点数で答えさせる。同じ300件で聞き方を磨き、別の期間で1回だけ確かめる。

## 対象

- 場の外 (9:00 より前、または 15:00 / 2024-11-05 からは 15:30 以後) に出た **業績予想の修正のお知らせ** (J-Quants の財務情報の種類が
  `EarnForecastRevision`)。**向き・幅は問わない**。同じ会社で同じ朝に入るものは1件にまとめる
- 次の朝の始値で売買できたもの (普通株、PRO・その他の市場を除く、開示の前の20営業日の平均売買代金 0.5億円以上、その日に値段が付いた)
- **組 a (磨く場所)**: 2016-11 〜 2019 の 3,356件からランダムに 300件 (種 0)。PDF が無いものは飛ばして次を取る
- **組 b (1回だけ確かめる)**: 2020 〜 2021-10 からランダムに 500件 (種 0)。磨き終わるまで読ませない
- 検証期間 (2021-11 〜 2024-10) は、組 b の結果を見てから別に宣言する

## 渡すもの

1. **数字の表** (scripts/stage2b_prepare.py で作る。開示の時点で分かっていたものだけ)
   - 通期の予想 (と上期の予想) の 修正前 → 修正後、変化、前期の実績との比較 (売上・営業利益・経常利益・純利益、連結が無ければ単体)
   - 決算期の何か月目か、同じ日に決算の発表があったか
   - 進み具合: 直近の四半期決算の累計実績 ÷ 修正前の通期予想、前期の同じ時点の累計 ÷ 前期の実績
   - 今期の予想がこれまでに何度変わったか (決算発表の中での変更も数える) と前回の向き
   - 開示の前の値動き: 入る日の前の取引日の終値までの 5・20・60 営業日 (TOPIX との差)
   - 会社の大きさ: ふだんの売買代金の帯 (組 a の母集団 3,356件の 1/3 ずつで 大・中・小)
2. **お知らせの本文**: 段階2a と同じ (pymupdf4llm で最初の3ページ、社名・コード・年・連絡先を伏せる)。
   年の伏せ方は、字の間に空白が入ったもの (「平 成30」「2 018 年」) も伏せるように直した (段階2a の 1,472件で、残る年 0件)

株価のその後、始値は渡さない。

## 読ませ方

- Claude Code のサブエージェント (Claude Opus 5.5)。30件ずつ、10本を同時に。ウェブ検索・ほかのファイルを見ることは禁止
- 質問文 (1回目。磨く中で変えたものは下の記録に残す):

```
あなたは日本株の運用担当です。下は上場会社が出した「業績予想の修正に関するお知らせ」と、
私たちが用意した数字の表です。社名・証券コード・年は伏せてあります。

売買のしかた: このお知らせを見て、次の取引日の朝の始値で買う(または売る)。持つのは数日〜20営業日。
注意: 修正の向きと大きさは、朝の始値の時点でほぼ値段に入っています。
知りたいのは「始値の後に、TOPIX と比べてさらに同じ向きに動くか、行き過ぎて戻るか」です。

考える順番 (答えに書かなくてよい):
1. 何がどれだけ変わったか (売上・利益、上か下か)
2. なぜ変わったか (本業の需要 / 費用 / 一時的な要因 / 会計上の要因)。その理由は来期も続くか
3. どれくらい意外か (決算期の何か月目か、進み具合、今期何度目の修正か)
4. 開示前の値動きから見て、すでに期待されていたか
5. 修正後の予想は、まだ控えめか、背伸びしているか

書かれている内容と表だけで判断し、この会社や後の株価について知っていることは使わないでください。

答え (1件につき JSON 1行):
{"qid": "...", "score": 整数, "conf": "低|中|高", "reason": "30字以内"}
score: +2 強く買い / +1 買い / 0 どちらでもない / -1 売り / -2 強く売り
```

## 成績の見方 (scripts/stage2b_aggregate.py)

- 値動き: 始値 → 1・5・20 営業日目の引け、TOPIX を引く、コスト前。**主に見るのは 20日**
- 見るもの:
  1. 点数と値動きの順位の相関 (件を選び直すブートストラップの 95% 範囲)
  2. 点数をランダムに入れ替えて、LLM 以上の相関になる割合
  3. 比べる相手: 数字だけ (営業利益 → 経常 → 純利益のうち変わった最初のものの修正率) の順位の相関
  4. 買い (+1, +2) の平均 − 売り (−1, −2) の平均
  5. 報告だけ: 上方・下方、会社の大きさ、自信の高さで分けた相関
- 300件だと、相関が 0.12 くらいより大きくないと偶然と区別できない。それより小さい差は、このやり方では見えない

## 磨き方のルール

- 組 a の同じ300件で、1回ごとに大きなところを1つだけ変える (材料を足す・減らす、考える順番を変える、など)。言い回しの細かい直しはしない
- **多くても5回**。毎回、変えた内容と結果を下の記録に残す
- 一番よかった回の聞き方で、組 b を **1回だけ** 読ませる。組 b で「LLM の 20日の相関の範囲の下限 > 0、かつ 数字だけの相関を上回る」なら、
  検証期間の宣言を書いて OK をもらう。満たさなければ、そこで止めて相談する
- 組 a・組 b はどちらも学習期間の中なので、ここで良くても「いける」とはしない

## 先に書いておく限界

- モデルが過去の値動きを覚えている恐れは消せない (ユーザーと合意のうえ、避けられない前提で進める)。会社が分かるかは聞かない
- 同じ300件で何度も直すと、その300件に合ってしまう。回数を5回までにし、組 b で確かめるのはそのため
- 本番で使うモデル (API で呼べる安いもの) とは別のモデルで読ませている
