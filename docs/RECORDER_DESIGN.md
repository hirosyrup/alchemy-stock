# 記録だけの仕組み (前向きの記録) の設計

2026-11-06 作成。まだ作っていない。注文は出さず、「このルールなら今ここで、この値段で入っていた」を毎日記録する。

## 1. 目的

シミュレーションで確かめていない次の点を、実際の時間の流れの中で記録して確かめる。

- 信号をその場で出せるか (後から分かる値段を使っていないか)
  - 例: 54 は始値で「−10% 以上の下げ」を判定しているが、本当は寄り付く前には始値が分からない
- Saxo の値段 (売値・買値) が、シミュレーションで使った J-Quants の始値・終値・ティックとどれだけずれるか
- 売りが止められている銘柄がどれくらいあるか
- 寄りの遅れ (特別気配) がどのくらい起きるか
- 49 で、開示から判断までに何秒かかるか (15:00 の集中時を含む)

記録の対象とルールは、検証で使ったものから変えない。

| 候補 | ルール (宣言どおり) | 記録で特に見ること |
|---|---|---|
| **54** | 前の取引日〜当日の寄り前に開示があり、始値 ÷ 前日の終値 − 1 ≤ −10%、前日の終値 200円以上、時価総額の上位 1,344 → 寄りで売り、5日目の終値で買い戻す | 寄り付いた直後の Saxo の売値と、J-Quants の始値の差。寄りが遅れた件数。売れない銘柄 |
| **49** | 取引時間中 (09:00〜11:29、12:30〜15:24) の業績予想の変更。営業利益 → 経常 → 純利益の順で最初に変わったもので、上がれば買い・下がれば売り。5秒後以降に入り、次の取引日の終値で手放す | 開示を見つけてから判断するまでの秒数。そのときの Saxo の値段と、ティックの「5秒後以降の最初の約定」の差 |
| **S16** | 立会外分売の発表 → 次の取引日の始値で売り、分売の日の始値で買い戻す | 件数が少ない (Saxo で年 3〜4件) ので、ついでに記録する |

## 2. Saxo のトークンを alchemy-fx と分け合う

### 今の alchemy-fx の仕組み (2026-11-06 に読んで確かめた)

- worker (Cloud Run、`alchemy-fx` プロジェクト、us-east1) の通信は、Cloud NAT の固定 IP から出ている
  - Saxo の認証サーバーの手前 (Akamai) が、Cloud Run の共用 IP を弾くため
- 15分ごとに Cloud Scheduler が `/refresh-token` を呼び、トークンを更新する
  - アクセストークンの有効期限は 20分
  - 更新すると古いリフレッシュトークンは使えなくなる。このため、2か所で更新すると片方が失効する
- 最新のトークンは Secret Manager の `saxo-access-token` と `saxo-refresh-token` に書き戻され、古い版は消される
- Cloud Run 上の worker 自身は更新せず、使うたびに Secret Manager から最新の版を読んでいる (`get_valid_token`)
  - 401 が返ったら読み直す (`reload_tokens`)

### 株の側のやり方: 読むだけ、更新は一切しない

```
alchemy-fx (固定 IP)                            alchemy-stock
  Scheduler 15分ごと                               記録係
      │                                               │
      ▼                                               │ 読むだけ
  worker /refresh-token ──書き戻す──▶ Secret Manager ◀─┘ (saxo-access-token の最新版)
                                         saxo-access-token
                                         saxo-refresh-token  ← 株の側には読む権限も渡さない
```

- 株の側は `saxo-access-token` の最新版を読むだけにする
  - 手元に置くのは最長 5分まで
  - 401 が返ったら1回だけ読み直してやり直す
- **`saxo-refresh-token` には読む権限すら渡さない**。権限で縛っておけば、株の側のコードに誤りがあっても更新できず、FX のトークンを失効させる心配がない
- 認証サーバー (logonvalidation.net) には一切つながない。データを取る窓口 (gateway.saxobank.com) は、固定 IP でなくても通る見込み (§6 の 0 で確かめる)
- 権限の付け方: 株の側のサービスアカウントに、`alchemy-fx` の `saxo-access-token` の1つだけ「読む」権限 (secretAccessor) を付ける
  - 付け足すだけで、FX 側の仕組みには手を入れない
  - ただし `alchemy-fx` の設定 (terraform) に1行増えるので、ユーザーの OK を取ってから行う

### 分け合うことで起きうること

| 起きうること | 対策 |
|---|---|
| FX のトークン更新が止まると、株の側も値段が取れなくなる | 株の側は「値段なし」で記録を続ける (開示を見つけた時刻などは残す)。FX 側には失敗の通知が既にある |
| 同じアプリ・同じ利用者なので、Saxo の回数の上限を FX と共有する。株の側が使いすぎると FX の注文が断られうる | 株の側は自分で上限を決める (全部で1分に 20回まで、値段は複数の銘柄をまとめて1回で取る。まとめて取る窓口 infoprices/list には別に1分に 30回の上限がある、2026-11-06 にヘッダーで確認)。429 (多すぎ) が返ったら長めに待つ |
| トークンは注文も出せる権限を持っている | 記録係のコードには、読む (GET) 以外の通信を作らない。窓口を包む部分で GET 以外を拒む |
| 株の CFD と FX は口座 (AccountKey) が別 | 記録では口座を使わない。将来注文するときは、株の CFD の口座の AccountKey を固定して、ほかの口座を拒む |
| 常時つなぎっぱなしの配信 (streaming) や、セッションの権限の変更が FX の取引に影響する恐れ | 使わない。REST で数秒おきに取りに行くだけにする |

### 開示の時刻の偏り (49 を見張る時間を絞れる理由)

学習期間 (2024-11〜2025-10) の 49 の出来事 (取引時間中の業績予想の変更、時価総額の上位 1,344) 278件を数えた (2026-11-06)。

- 開示の時刻 (分まで) が **ちょうど :00 が 78%、:30 が 15%、それ以外は 7%**
- 時間帯は 13時台 71件・14時台 92件・15時台 87件で、午後に集中。午前は 9〜11時台で 20件
- 出来事があったのは 74日 / 約240日。1日あたり中央 2件、最大 21件

:00・:30 以外も、ほぼ全部が 5分刻み (:10・:20・:40 が多く、:15・:45 も少し)。全部の会社の 758件で、5分刻みでないのは 1件 (:17) だけ。
:00・:30 以外の 20件 (上位 1,344) は、学習期間で 1回 +2.55%・中央 +2.97% (19件、翌日の始値まで) で、トヨタなど大きな会社が多い。見逃してよい残りものではない。

一覧に出るまでの秒数 (2026-11-06 の見張り、142件): その分になってから 0.3〜2.5秒。ただし 41件が一度に出た 13:00 は、一覧の読み込みが遅れて 17秒後。

同じ時刻の開示は一度にまとめて出ていた (11:30 の 22件、13:00 の 41件など、どの時刻も最初と最後に見えた秒が同じ。後から同じ時刻の表示で足されたものは無かった)。

このため取引時間中ずっと見張らず、**5分刻みの時刻ごとに、1分前に起動して見張る**。

- その時刻の開示が一覧に出たら、処理して、念のため 10秒見てから終わる
- その時刻から 1分たっても何も出なければ終わる (今日の一番遅い 13:00 でも 17秒。遅れて出たものは夜の答え合わせで分かる)
- 「同じ時刻の開示は一度に出る」はまだ半日分しか見ていない。夜の答え合わせで1日の一覧と突き合わせ、後から同じ時刻で出たものを数えて確かめ続ける
- 2026-11-06 の 15:00 は 59件が 1.15秒後にまとめて出た (13:00 の 17秒は TDnet 側の応答の遅さだったらしい)。見張りを始めた後 (10:05〜15:15) の開示は、1日の一覧 (302件) と突き合わせて取りこぼし 0件
- XBRL を読み終えるまで (その分になってから、2026-11-06): ふだん 1.5〜3秒、15:00 は 4.2〜5.0秒 (業績予想の修正 2件は約 4.5秒)。ただし 13:00 は TDnet 側が遅く 27〜28秒、13:30 は 7〜18秒。49 の「5秒後以降に入る」に間に合わない時刻が日によって出るので、毎回の秒数を記録して割合を数える
- 15:30 (引け後) は 242件が 3ページに分かれていたが、3.4秒で全部見えた
- 一覧は新しい順に 100件ずつのページ。決算の集中する日は 15:00 だけで 100件を超えうるので、1ページ目が新しい開示で埋まったら 2ページ目以降もすぐ読む

## 4. 記録する中身

Firestore (`alchemy-stock-513407` の Firestore、FX とは別) に置く。本番で注文を出すようになっても、建玉や注文の状態の置き場としてそのまま使える。分析するときは手元に書き出して DuckDB で読む。

- 値段を数秒おきに取った結果を全部は書かない (書き込みの回数を抑える)。判定に使った値段と、入る・手放すときの値段だけを書く
- 量は1日に数十〜数百件の書き込みの見込みで、無料の枠 (1日 書き込み 2万・読み取り 5万) に収まる

コレクション (表) は次のとおり。

- `signals`: 候補・会社・向き (買い/売り)、判定に使った値 (下げの率、予想の新旧)、元の開示の時刻と ID
- `quotes`: 見た時刻、Saxo の売値・買値・最後の値段・値段の時刻、売りが止められているか
- `latency` (49): 開示の時刻 (一覧の表示)、一覧で見つけた時刻、XBRL を読み終えた時刻、判定した時刻、値段を取った時刻
- `paper_trades`: 入った時刻と値段、手放した時刻と値段、Saxo の保有コストの見込み
- `reconcile`: 同じ取引のシミュレーションの値段 (J-Quants) と記録の値段の差、件数の食い違い (片方にしかない取引とその理由)
- `errors`: 値段が取れなかった、トークンが切れていた、寄らなかった、など

東証の規約のため、株価を含む記録は自分だけが読める場所に置き、人に見せるページや公開のリポジトリには載せない。

## 5. どこで動かすか

| 案 | 中身 | 費用の見込み | 良い点・悪い点 |
|---|---|---|---|
| **A. 手元の Mac** | 取引時間中に Mac で動かす | 0円 | すぐ始められる。スリープ・外出で止まる |
| **B. GCP (`alchemy-stock-513407`、東京)** | Cloud Scheduler から Cloud Run の job を必要な時間だけ起動する: 朝 (08:30〜寄りの記録が終わるまで、最長 60分)、49 の窓 (5分刻みの時刻の 1分前から。開示が出たら 10秒後、出なければ 1分後に終わる。1日 65回)、引け前 (15:18〜15:25)、夜 (答え合わせ)。記録は Firestore | job は CPU 1つが最低 (0.5 などは service だけ)。1日 合計 約9,000秒 (2.5時間) × 21日 ≒ 19万 vCPU秒で、無料の枠 (月 18万 vCPU秒) をわずかに超えて月 数十円。メモリ 0.5GB は 約9.5万 GB秒で枠 (36万) の中 (job にも枠が効くか、東京の値段の区分は移すときに公式の料金ページで確かめる)。Cloud Scheduler は請求先アカウントで 3つまで無料で FX がすでに使っているため、株の側の 4つで月 約60円 | 止まらない。FX とプロジェクトが分かれ、FX の本番に影響しない。固定 IP は要らない (トークンを更新しないため)。job の起動に数十秒かかるので、窓の 1〜2分前に起動する |

**別のプロジェクトから FX のトークンを読む方法**: `alchemy-stock-513407` に記録係用のサービスアカウントを作り、`alchemy-fx` の `saxo-access-token` という1つのシークレットにだけ、そのサービスアカウントの「読む」権限を付ける。Cloud Run の job はそのサービスアカウントとして動くので、鍵のファイルは要らない。コードからは `projects/alchemy-fx/secrets/saxo-access-token/versions/latest` を読む。手元で動かすときは自分の Google アカウントの権限で読む。

おすすめの順番は次のとおり。

1. A で作り、数日動かして直す
2. B に移して、数か月止めずに記録する

B を作るとき (お金がかかり、FX 側の権限に1行足す) は、その前に改めて OK をもらう。

## 6. 進め方

0. **確かめること (読むだけ、お金はかからない)**
   - 東証の Level1 が有効になっていて、本番のトークンで日本株 CFD の値段 (infoprices) が取れるか。2026-11-05 の時点では `NoAccess` だった
   - データの窓口が、手元の Mac (固定 IP でない) から通るか
   - 寄る前・特別気配の間に Saxo の値段がどう見えるか (始値の前に何が返るか)
   - 売りが止められていることが、銘柄の情報で分かるか
1. 手元で 54 と S16 (朝と引けの記録) を作る。過去の日付で `rules.py` が `run_stage4.py` と同じ候補を出すことを確かめる
2. 手元で 49 (取引時間中の見張り) を足す。XBRL の読み取りは今日の試しを流用する
3. 夜の答え合わせを作る
4. GCP に移す (OK をもらってから)
5. 月に1回、記録を見る: 入った値段のずれ、件数の食い違い、売れなかった件数、49 の秒数

記録の結果を合否の判定に使うかどうか、使うならどの基準で見るかは、見る前に別に決める (今の決まりと同じく、見る前に宣言する)。

## 7. 決めていないこと・分かっていないこと

- 54 の「開示があるか」は、検証のコード (`run_stage4.py` の `has_disc`) では日付だけで見ており、その日の寄った後に出た開示も数えている。本番では寄る前の開示しか使えない。記録では寄る前の開示で判定し、「その日のうちに後から開示が出た会社」も別に数えて、ずれの大きさを見る
- ルールの書き直し (`src/alchemy_stock/recorder/rules.py`) の突き合わせ (2026-11-06、`scripts/check_recorder_rules.py`、2024-06〜2026-10):
  - 検証と同じ条件では、54 は 418件、S16 は 113件が、検証のコードと1件残らず一致した
  - 本番の条件で変わるのは、54 で 1件増える (調整前の終値で 200円を見るため)、S16 で 1件増える (30暦日の期限切れ) だけ
  - 54 の 419件のうち 40件 (10%) は、開示がその日の日付しかなく、寄った後の開示で判定されていた可能性がある。うち 20件は暴落の日 (2024-08-05 が 11件、2025-04-07 が 9件) で、市場全体の下げに、その日の午後の決算や自己株の開示が重なっていたもの。本番ではこれらの一部が対象外になる

- Saxo の値段の回数の上限の正確な値 (FX と合わせた余裕)。0 の確かめで、応答のヘッダーから読む
- 寄り前の値段の見え方。Saxo が寄り前の気配を出さないなら、54 は「寄った後の最初の値段」で入る形になる (宣言の「寄り」とは少しずれるので、そのずれ自体を記録する)
- 49 の「前の予想」は、J-Quants の決算の資料から作る。J-Quants にまだ入っていない直前の開示があると、比べる元がずれうる
- 5日目の終値で手放すとき、CFD で引けのオークションに注文を出せるか。記録では 15:24 の値段と終値の両方を残す
